🌳 AVL Tree — เช็คสมดุลด้วย Balance Factor

AVL (Adelson-Velsky และ Landis) คือ BST แรกที่ self-balancing ในโลก กฎมันเด็ดขาดว่า:

📗พื้นฐานที่ต้องท่อง
  • height(node): ใบ = 0, node ปกติ = 1 + max(height ลูกซ้าย, height ลูกขวา), ช่องว่าง (null) = −1
  • Balance Factor (BF) = height(ซ้าย) − height(ขวา) — ค่าที่อนุญาต: −1, 0, +1 เท่านั้น
  • BF > 0 = ถนัดซ้าย (left-heavy), BF < 0 = ถนัดขวา (right-heavy)
  • ต้นที่เป็น AVL มีความสูง h < 1.44 log₂ n — "สวยพอ" และ search/insert/delete ยัง O(log n)

🔄 4 เคสหมุน (หัวใจที่สุดของบท)

เมื่อ insert/delete ทำให้ node ไหน BF เป็น ±2 เรา "หมุน" แก้ตรงจุด — ชื่อเคสตั้งตาม "ทางเดินของเส้นทาง insert 2 ก้าวสุดท้าย":

เคสรูปแบบวิธีแก้จำง่าย
LLซ้าย-ซ้าย (BF +2, ลูกซ้าย BF ≥ 0)หมุนขวา ที่ nodeเคส "นอก" (outside) — หมุนเดียวจบ
RRขวา-ขวา (BF −2, ลูกขวา BF ≤ 0)หมุนซ้าย ที่ nodeเคส "นอก" — หมุนเดียวจบ
LRซ้าย-ขวา (BF +2, ลูกซ้าย BF < 0)หมุนซ้ายที่ลูกซ้าย แล้วหมุนขวาที่ nodeเคส "ใน" (inside) — หมุน 2 ครั้ง
RLขวา-ซ้าย (BF −2, ลูกขวา BF > 0)หมุนขวาที่ลูกขวา แล้วหมุนซ้ายที่ nodeเคส "ใน" — หมุน 2 ครั้ง
⚠️วิธีจำให้ไม่งง

ดู "2 ก้าวสุดท้ายของเส้นทาง insert": ถ้าตรงกัน (LL/RR) = เคสนอก หมุนรอบเดียวสวนทาง (LL→ขวา, RR→ซ้าย) ถ้าเลี้ยว (LR/RL) = เคสใน หมุนสองรอบ: รอบแรกทำให้เส้นทางตรงก่อน แล้วจบเหมือนเคสนอก

ขั้นตอน insert ของ AVL ครบทุกข้อ (ทำในข้อสอบตามนี้เป๊ะ)

1. insert ลงแบบ BST ปกติเดินซ้าย/ขวาตาม BST property แล้ววางเป็นใบ
2. เดิน "ขึ้น" ตามเส้นทาง คำนวณ BF ทุก nodeหลังวางใบ height ของบรรพบุรุษเปลี่ยนได้ — เริ่มจากพ่อของใบใหม่ขึ้นไปจนถึง root
3. เจอ node แรกที่ |BF| = 2 → หมุนที่ node นั้นเลือกเคสจาก 2 ก้าวสุดท้ายของเส้นทาง (LL/RR/LR/RL) — หมุนครั้งเดียว (เดี่ยวหรือคู่) ก็จบ ทฤษฎีบท AVL การันตี (insert ต้องหมุนมากสุด 1 ชุด; delete ต่างหากอาจต้องหมุนไล่ขึ้นทุกชั้น)
4. อัปเดต height ของ node ที่เกี่ยวข้องหลังหมุน height เปลี่ยน — ถ้าเขียนโค้ดให้ recompute เสมอ (เดี๋ยวดูโค้ดข้างล่าง)

🧪 สร้าง AVL จากสไลด์: 21, 26, 30, 9, 4, 14, 28, 18, 15, 10, 2, 3, 7

ดูภาพ "ก่อน → หลัง" ของทุกจุดที่หมุน (ตัวเลขในวงกลมแดง = node ที่ BF พัง ณ ตอนนั้น):

💻 โค้ดหมุน (จากสไลด์) + การลบ AVL

// node class เก็บ height ทั้งสองฝั่ง (ตามสไลด์)
class TreeNode {
  int data, h_left=-1, h_right=-1;
  TreeNode left=null, right=null, parent=null;
}

// Left Rotation (แก้ RR) — หมุนที่ n: ลูกขวา p ขึ้นมาแทน
void rotationFromRight(TreeNode n) {
  TreeNode p = n.right;
  n.right = p.left;          /*1*/  // subtree กลาง (ลูกซ้ายของ p) ย้ายไปเป็นลูกขวาของ n
  if (p.left != null) p.left.parent = n;  /*2*/
  if (n == root) { root = p; p.parent = null; }       /*3a*/
  else {
    p.parent = n.parent;                                  /*3b*/
    if (n.parent.left == n) n.parent.left = p;            /*4*/  // แม่ชี้มาที่ p แทน
    else n.parent.right = p;
  }
  p.left = n;                /*5*/  // n กลายเป็นลูกซ้ายของ p
  n.parent = p;              /*6*/
  // …จากนั้น update h_left/h_right ของ n และ p ใหม่เสมอ!
}

// Double rotation (แก้ RL): แก้ลูกก่อน แล้วค่อยแก้แม่
void doubleRotationFromRight(TreeNode n) {
  rotationFromLeft(n.right);   // หมุนซ้ายที่ลูกขวา → เส้นทางตรงเป็น RR
  rotationFromRight(n);        // หมุนซ้ายที่ n ตามสูตรเคสนอก
}
📗หลักการหมุน (อ่านแล้วเขียนได้ทุกเคส)

หมุนซ้ายที่ n = ยก ลูกขวาขึ้นมาแทน; หมุนขวาที่ n = ยก ลูกซ้ายขึ้นมาแทน — สิ่งที่ต้องทำเสมอ 4 อย่าง: (1) subtree "กลาง" ของลูกที่ถูกยก ย้ายไปติดกับตัวถูกกด (2) แม่เดิมชี้มาที่ตัวขึ้นใหม่ (3) ต่อ parent ให้ครบ (4) อัปเดต height ให้ตัวถูกกดและตัวขึ้นใหม่ (นับจากล่างขึ้นบน)

การลบของ AVL: ลบแบบ BST ก่อน แล้ว "เดินขึ้นจากจุดลบ ตรวจ BF ทุกบรรพบุรุษ — เจอพังก็หมุน แล้วเดินต่อไปอีก" เพราะการหมุนหนึ่งครั้งอาจเปลี่ยน height ทำให้ชั้นบนพังตาม (ต่างจาก insert ที่หมุนครั้งเดียวจบ) — โครงเงื่อนไขจากสไลด์:

n.height = 1 + Math.max(height(n.left), height(n.right));
int bf = getBalance(n);
if (bf > 1 && getBalance(n.left) >= 0)  return rightRotate(n);        // LL
if (bf > 1 && getBalance(n.left) < 0)  { n.left = leftRotate(n.left);  // LR
                                          return rightRotate(n); }
if (bf < -1 && getBalance(n.right) <= 0) return leftRotate(n);       // RR
if (bf < -1 && getBalance(n.right) > 0)  { n.right = rightRotate(n.right); // RL
                                            return leftRotate(n); }

สังเกต: เคสนอก (LL/RR) ดู "ลูก BF ≥ 0 / ≤ 0" — การลบต่างจาก insert ตรงที่ลูก BF = 0 ก็ใช้เคสนอกได้ (ลบแล้ว height ของลูกคงเดิม)

สูงไม่เกิน 1.44 log₂n → search/insert/delete = O(log n) การันตี · แลกมาด้วยต้นทุนจัดการ: เช็ค BF ทุกชั้นบนเส้นทาง (สูงสุด ~1.44 log₂n ครั้ง) และ delete อาจหมุนไล่ขึ้นหลายชั้น (insert หมุนมากสุด 1 ชุด) — เหมาะกับงานที่ ค้นหาถี่

🎨 Red-Black Tree — สมดุลด้วย "การเปลี่ยนสี"

อีกตระกูล self-balancing BST ที่ Java TreeSet/TreeMap ใช้จริง — ไม่เก็บ height แต่เก็บ สี (red/black) ในแต่ละ node แล้วบังคับกฎ 5 ข้อ:

📗กฎ 5 ข้อของ Red-Black (ท่องให้ได้!)
  1. เป็น BST (ซ้ายน้อย ขวามาก) อยู่แล้ว
  2. ทุก node มีสี แดง หรือ ดำ เพียงสีเดียว
  3. root ต้องดำเสมอ
  4. แดงต้องไม่มีลูกแดง (ห้าม "แดงติดกัน" บนเส้นทางเดียว)
  5. ทุกเส้นทางจาก node ใด ๆ ลงไปถึงใบ NIL ต้องมีจำนวน node ดำเท่ากันหมด (เรียกว่า black-height เท่ากัน) · ใบ NIL นับเป็นดำ
💡เปรียบเทียบ: ทำไมกฎแดง-ดำ = สมดุล?

กฎ "black-height เท่ากัน" ทำให้ทุกเส้นทางมีจำนวน "ชั้นดำ" เท่ากัน และกฎ "แดงไม่ติดกัน" ทำให้แทรกแดงระหว่างดำได้แค่ตัวเดียว → เส้นทางยาวสุด ≤ 2 เท่าของเส้นสั้นสุด → สูงไม่เกิน 2 log₂(n+1) → ยัง O(log n)! เหมือนอาคารที่ชั้น "ดำ" ทุกตึกเท่ากัน แต่อนุญาตให้แทรก "ชั้นแดง" (mezzanine) ได้ไม่เกินชั้นละ 1 — ตึกจึงบิดเบี้ยวได้ไม่เกิน 2 เท่า

✅ ต้น A: ทุกเส้นทาง root→NIL มีดำ 3 ตัว (40B + 20B/60B + NIL) → valid · ต้น B: เส้นทางผ่าน 70B มีดำ 4 ตัว ≠ เส้นอื่น → invalid — การ "ทำให้ดำเพิ่ม" ทำลาย black-height ทันที

➕ RB Insert — แดงใหม่เข้ามา แล้วแก้ตาม "สีของลุง"

insert แบบ BST ปกติ แต่ node ใหม่เป็นสีแดงเสมอ (แดงใหม่ไม่เปลี่ยน black-height เลย — อัลกอริทึมจึงไม่ต้องไล่วัดเส้นทาง) แล้วเช็คแค่ "แดงติดแดง" ไหม:

สถานการณ์หลัง insertเป็นปัญหาไหมวิธีแก้
พ่อเป็น ดำไม่มีปัญหาจบทันที ✅
พ่อแดง + ลุงแดงแดงติดแดง (ปัญหา "สี")Recolor: พ่อ+ลุง → ดำ, ปู่ → แดง แล้วขยับไปตรวจที่ปู่ต่อ (อาจลามขึ้นไปถึง root · ถ้าปู่เป็น root กลับเป็นดำ)
พ่อแดง + ลุงดำ/NILแดงติดแดง (ปัญหา "รูปทรง")หมุนที่ปู่ (LL/RR เดี่ยว, LR/RL คู่) + recolor: ตัวขึ้นใหม่ → ดำ, ปู่ → แดง แล้ว จบ
💡จำเคล็ด

"ลุงแดง = ปัญหาสี → เปลี่ยนสี ขยับขึ้น" · "ลุงดำ = ปัญหารูป → หมุน แล้วจบ" — การ recolor ไม่เปลี่ยน black-height (ดำคู่แลกปู่แดง) ส่วนการหมุนแทน "ดำปู่" ด้วย "ดำตัวขึ้นใหม่" black-height จึงคงเดิมเช่นกัน จบด้วย root.color = BLACK เสมอ

Trace จากสไลด์: insert {10, 20, 30, 15, 25, 27, 5, 1, 7} ทีละค่า

1. insert 10 (แดง)เป็น root → ผิดกฎ root ดำ → recolor เป็นดำ → 10B
2. insert 20 (แดง)พ่อ (10B) ดำ → จบ → 20R อยู่ขวาของ 10B
3. insert 30 (แดง) → แดงติดแดง 20R-30R, ลุง NIL (ดำ) → เคส RRหมุนซ้ายที่ปู่ 10 · recolor: 20→B, 10→R · ผล: 20B(10R, 30R)
4. insert 15 (แดง) → แดงติดแดง 10R-15R, ลุง 30R แดง → recolor10→B, 30→B, ปู่ 20→R → แต่ 20 เป็น root → บังคับกลับดำ · ผล: 20B(10B(−,15R), 30B)
5. insert 25 (แดง)พ่อ (30B) ดำ → จบ · 25R อยู่ซ้ายของ 30B
6. insert 27 (แดง) → แดงติดแดง 25R-27R, ลุง NIL (ดำ) → เคส LRหมุนซ้ายที่ 25 (27 ขึ้น) → หมุนขวาที่ 30 (27 ขึ้น) · recolor: 27→B, 30→R · ผล: 20B(10B(−,15R), 27B(25R,30R))
7. insert 5 (แดง)พ่อ (10B) ดำ → จบ · 5R ซ้ายของ 10B
8. insert 1 (แดง) → แดงติดแดง 5R-1R, ลุง 15R แดง → recolor + ลามขึ้น5→B, 15→B, ปู่ 10→R · ไปตรวจที่ 10: พ่อของ 10 คือ 20B ดำ → หยุด · ผล: 20B(10R(5B(1R,−),15B), 27B(25R,30R))
9. insert 7 (แดง)พ่อ (5B) ดำ → จบ · 7R ขวาของ 5B — ครบ 9 ค่า ✅

เวลาการทำงาน: search/insert/delete ของ RB ล้วน O(log n) — insert ใช้การหมุนมากสุด 2 ครั้ง (ข้อดีเด่นกว่า AVL ตอน delete ที่อาจหมุนไล่ขึ้นหลายชั้น) จึงเป็นที่นิยมใน library: Java TreeSet/TreeMap (sorted set/map: ไม่เก็บของซ้ำ, ไล่ตามลำดับ ascending, มี first()/last()/contains()/remove()) ก็สร้างบน Red-Black tree นี่เอง

🧲 Splay Tree — ไม่แคร์สมดุล แต่ "ดึงของที่เพิ่งใช้ขึ้นหัว"

Splay tree คือ BST ที่พอ access (search/insert/delete) node ไหน จะ splay = หมุนดึง node นั้นขึ้นมาเป็น root เสมอ (โดยไม่ทำลายกฎ BST) — ไอเดียจริง ๆ มาจากข้อมูลโลกจริง: "ของไม่กี่ชิ้นถูกเรียกใช้บ่อยมาก" (80/20 rule) พอ splay แล้วของยอดฮิตจะลอยอยู่บน ๆ ค้นครั้งหน้าไวมาก ของที่ไม่ค่อยใช้ค่อย ๆ จมลงล่าง

💡เปรียบเทียบ

เหมือนตู้เสื้อที่ไม่มีใครจัดชั้น: เสื้อที่เพิ่งใส่เมื่อวานถูก "ยกไปแขวนข้างประตู" ทุกครั้ง เสื้อจามรุ่นลาวค่อย ๆ ถูกดันไปมุมลึก — ไม่มีความสวยงามเรขาคณิต แต่เร็วต่อ "การใช้งานจริง"

การทำงานของ Splay แต่ละ operation

Searchค้นแบบ BST ปกติ → เจอแล้ว splay ตัวที่เจอขึ้น root · ถ้าไม่เจอ ให้ splay "node สุดท้ายที่ผ่าน" ขึ้นแทน (ตัวนั้นใกล้ค่าที่หามากสุด)
Insertแทรกแบบ BST → splay ตัวใหม่ขึ้น root ทันที (insert ล่าสุดอยู่บนสุดเสมอ)
Delete — แนวออกสอบ (Final 67!)(1) search ตัวที่จะลบ แล้ว splay มันขึ้น root (2) หา max ของ subtree ซ้าย แล้ว splay ขึ้นเป็น root ของ subtree ซ้าย (3) ต่อ subtree ซ้ายนั้นเป็น root ใหม่ โดยให้ลูกขวาของ root ใหม่ = ลูกขวาเดิมของ root เก่า (subtree ขวาทั้งก้อนแขวนต่อขวา) — จบ ไม่ต้อง recolor, ไม่ต้องนับ height
📗Amortized analysis — เวลาของ splay นับยังไง

แต่ละ operation เดี่ยว ๆ อาจแย่ (worst O(n) — ต้นเอียงได้ ไม่มีใครห้าม) แต่เฉลี่ยต่อ operation ในลำดับยาว ๆ ดีเสมอ: ทำ M operations บนต้น N node ใช้รวม O(M log N) → amortized O(log N) ต่อ operation · การรับประกันนี้มาจากการ splay เอง (ไม่ต้อง bookkeeping height/BF/สีเลย!) — คำสำคัญ "amortized" ออกเติมคำบ่อย
